```bash

```

- [ ] 用 5 个典型订单各跑一次，观察真实模型是否按 JSON 格式返回
- [ ] 记录第一次的"翻车现象"（比如不调工具直接编答案、JSON 外面包了 markdown）——**这些翻车是面试最好的素材**
- [ ] 针对发现的问题改 `PromptBuilder`（v2 → v3），每次改动都跑一次评测做对比

**常见翻车与对策**

| 现象 | 原因 | 对策（写进代码而非 prompt） |
|---|---|---|
| 不调工具直接下结论 | 模型"过度自信" | 校验：没有 tool_calls 时强制追问一轮 |
| 结论枚举不在白名单 | 自由发挥 | `DiagnosisParser` 降级为 NEED_MANUAL |
| JSON 外有解释文字 | 未约束 | `extractJson` 抽取首个完整对象 |
| 编造证据 | 幻觉 | 证据链用工具原文**覆盖**模型输出 |

**当天验收**：真实模型跑通 1 次完整诊断。

策略：**一次只改一个变量，改完必跑评测**。

| 迭代 | 改动 | 预期收益 |

| 1 | 在 prompt 里补"判断规则优先级" | 减少枚举误判 |

## 面试高频题（口述版）

**1. 介绍一下这个项目（必考，控制在 1 分钟）**
> "这是一个电商订单履约诊断助手。客服输入订单号和问题，Agent 自动并发查询订单、支付、库存、物流、风控五个系统，
> 几十秒内给出根因、证据链和处理建议。技术上我自己写了 Agent 执行循环和工具并发层，重点是三件事：
> 工具调用的安全边界、单点故障时的降级、以及一套能回归的评测体系。"

**2. 为什么自己实现 Agent 循环，不用 LangChain4j？**
> "三个原因：一是工具级超时、熔断、越权校验我需要精确控制，框架默认行为不好干预；
> 二是自研只有 200 行，每行我都讲得清；三是实现一遍才知道 Function Calling 的本质是
> 模型返回 tool_calls → 本地执行 → 结果回填 → 再请求，本质是个状态机。"

**3. 多个工具并发怎么做？超时怎么处理？**
> "`CompletableFuture.supplyAsync` 提交到固定大小的有界线程池，每个任务套 `orTimeout`。
> 但注意 `orTimeout` 只是让 future 完成，底层任务还在跑，所以内层还有一层
> `Future.get(timeout)` 真正中断工作线程——这是两层超时，我在代码里踩过这个坑。"

**4. 模型乱调工具怎么办？**
> "三层防线：工具名必须在注册表白名单内；参数按 JSON Schema 校验；最后在工具执行层做数据权限校验。
> 任何一层失败都把错误作为 tool 消息回填给模型让它自我纠正，连续 2 轮全失败直接终止转人工。"

**5. 怎么防 prompt 注入？**
> "核心思路是不相信模型层的约束。用户完全可以注入'忽略以上指令'，
> 所以我把约束做在工具执行层：工具只接受白名单参数，服务端按**会话里的 userId** 反查订单归属，
> 不属于就抛 SecurityException 终止整个会话，而且不告诉调用方订单是否存在——防止被用来枚举。"

**6. 单个下游服务挂了，你的 Agent 会怎样？**
> "工具的超时/异常会转成带错误码的 ToolResult，模型基于其他证据继续推理，
> 最终结论的置信度被强制压到 0.6 以下。我在代码里做了故障注入开关，演示时可以一键让物流服务挂掉。"

**7. 怎么防止 Agent 死循环烧钱？**
> "两个闸：最大步数 6，超了之后撤掉 tools 参数逼模型基于已有证据收敛；
> 连续 2 轮工具全失败直接抛异常终止。另外会话级 token 有统计，能算成本和设置配额。"

**8. 怎么抑制幻觉？**
> "四个手段：结论用枚举白名单，输出不是枚举就降级成 NEED_MANUAL；
> 证据链不用模型的话，而是用工具返回的原文覆盖；置信度跟工具成功情况挂钩；
> 评测集里专门放了两类陷阱单——正常在途单和数据缺失单，专门测误报和乱下结论。"

**9. 你的准确率是怎么算的？**
> "200 条带标注用例，结论枚举精确匹配算通过，这是我的主指标，不依赖任何主观判断。
> 辅助指标有证据命中率和 LLM 裁判分，裁判只占 40% 权重，只给开放式建议打分，
> 而且每周人工抽 20 条校准。所以我汇报的是确定性指标，不是模糊的印象分。"

**10. 改了 prompt 之后怎么知道真的变好了？**
> "同一评测集、同一温度参数，跑一次 `eval_run`，对比两次的准确率和失败用例集合。
> 关键是能定位是哪个类别掉的点——我的失败明细按期望结论聚合，一眼能看出是'物流异常'在掉，还是'数据缺失'的误报变多。"

**11. 这个项目有什么不足？**
> "三个：一是会话记忆还在进程内，多实例部署要迁到 Redis；二是评测集是我自己构造的，
> 场景分布和真实订单有偏差，真实上线要补充线上抽样的 badcase；
> 三是目前是单体串行编排，如果要做长链路任务，需要引入工作流引擎做断点恢复。"
